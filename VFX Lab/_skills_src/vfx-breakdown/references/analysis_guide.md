# 영상 분석 가이드

이 문서는 1단계(측정)와 2단계(해석)를 할 때 읽는다. 목표는 "이 이펙트가 왜 좋아 보이는가"를 **프레임 번호와 수치로** 설명하는 것이다.

## 목차
1. 측정값의 뜻
2. 진행 순서
3. 무엇을 보나 (핸드북 장별 렌즈)
4. 해석 규칙
5. 자주 나오는 함정
6. 평가 쓰는 법 (총평 · 검사표 · 항목 구조)
7. 유형별 렌즈: 투사체

---

## 1. 측정값의 뜻

extract.py가 만드는 `data.json`은 프레임마다 18개 값을 가진다.

| 번호 | 값 | 뜻 |
| --- | --- | --- |
| 0 | 화면 평균 L* | 화면 전체 지각명도 평균. 노출 상승·암전·반전 프레임을 잡는다 |
| 1 | 이펙트 상위 5% L* | 이펙트 픽셀(기준 프레임 대비 ΔE>10) 중 밝은 쪽 5% |
| 2·3 | ROI A·B 최대 L* | 두 영역(예: 시전체·대상) 99번째 백분위. "누가 주인공인가" |
| 4·5·6 | 코어·바디·엣지 색상 | 각 밝기 단계 픽셀의 HSV 색상 원형 평균(°) |
| 7·8·9 | 코어·바디·엣지 면적 % | 이펙트 픽셀 중 각 단계 비율 |
| 10 | 이펙트 면적 % | 화면 대비 |
| 11 | 화면 색상 | 화면 전체 색상 평균(장면 틴트) |
| 12 | 강도 | 화면에서 L* 45를 넘는 만큼의 평균. 타이밍 분석의 기본 곡선 |
| 13·14·15 | 코어·바디·엣지 대표색 | 각 단계 RGB 중앙값 hex |
| 16 | 화면 평균색 | hex |
| 17 | 상위 0.2% L* | 가장 밝은 점 |

밝기 단계: 코어 L* 85–100 · 바디 60–85 · 엣지 35–60 · 헤이즈 22–35.

**페이지·노트에 쓰는 이름.** 처음 읽는 사람이 바로 알아보게, 글에는 측정 기호 대신 아래 말을 쓴다. 페이지 맨 위 "읽는 법" 카드가 이 세 가지를 그림으로 설명한다.

| 글에 쓰는 말 | 측정값 | 뜻 |
| --- | --- | --- |
| 명도 | L\* (0–100) | 흑백으로 바꿨을 때의 밝기. 0 검정, 100 흰색 |
| 선명도 | C\* (0–100 안팎) | 눈에 보이는 채도. 0이면 회색, 클수록 진하다 |
| HSV S | HSV S (0–100 또는 0–1) | 색 선택기(포토샵·엔진 피커)의 채도(Saturation) 숫자. 같은 HSV S라도 색에 따라 선명도가 다르다 |
| 색상 | HSV 색상 각도(0–360°) | 색상환 위의 위치. 글에는 색 이름을 같이 쓴다: "파랑(215°)" |

- 글(제목, 관찰, 왜, 근거 칩, 가져오기, 캡션)에는 L\*, C\*, Lab을 쓰지 않는다(HSV S는 그대로 쓴다). 측정 방법 문단과 measure.py 출력에만 남는다. measure.py 출력도 이 이름으로 나온다.
- HSB의 B는 "밝기 값"이라고 부르고 명도와 섞지 않는다.
- 색상 각도는 페이지에서 자동으로 앞에 색 점이 붙고, 마우스를 올리면 색상환에 위치가 뜬다. 색 이름은 직접 쓴다(점만으로는 이름을 모른다).
- 색상 **차이**는 "81° 회전"처럼 회전·차이 같은 말을 붙인다. 그래야 색 점이 붙지 않는다(차이는 색이 아니다).
- 페이지에서 주요 색상 2–4개를 `key_hues`로 주면 "읽는 법" 색상환에 표시된다.

## 2. 진행 순서

1. **전체를 본다.** 컨택트 시트(`contact_*.jpg`)를 전부 Read로 본다. 한 장에 48프레임. 건너뛰지 않는다. 이 단계에서 무슨 일이 일어나는지 줄거리를 잡는다.
2. **흐름 숫자를 본다.** `measure.py WORK summary`, `measure.py WORK peaks`. 강도 피크, 피크 직전에 밝기가 내려가는 프레임(밝기 누르기 후보), 화면 평균 L*가 튀는 프레임(노출 상승·반전)을 찾는다.
3. **막과 비트를 나눈다.** 막은 서사 단위(3–5개), 비트는 동작 단위(10–30개). 경계는 강도 곡선이 꺾이거나 형태가 바뀌는 프레임. 막마다 한 단어 이름(봉인, 전환, 폭파, 여운 같은).
4. **경계와 디테일은 원본 해상도로 확인한다.** `measure.py WORK strip 38,39,40,46,47 out.jpg [--crop x,y,w,h]`(crop은 스프라이트 셀 좌표, 다른 명령·config와 같다). 1프레임 단위 사건(플래시, 누르기, 반전)은 꼭 직접 본다.
   녹화 드롭으로 같은 프레임이 반복되는지 `measure.py WORK dupes`로 확인한다. 나오면 그 구간 타이밍은 ±1f로 표시한다.
5. **색을 잰다.** 막·구간별 `palette`, 색이 바뀌는 구간은 `hue a-b`, 상태 변화 전후는 `lstats`, 끝부분은 `scene`.
6. **주목을 잰다.** ROI가 있으면 `focus 1-N --relative`. 두 물체의 원래 밝기가 다르면 원값 비교는 이펙트와 상관없이 한쪽이 이긴다. 기준 프레임 대비 상승량으로 본다. 단, 원래 밝은 쪽은 천장(L* 100) 때문에 상승량이 작게 나오니 원값(`focus a-b`)도 같이 보고 화면으로 판단한다. 작은 물체는 ROI 최대 L*가 "밝기"보다 "밝은 면적"에 끌려가니 상위 5% L*와 같이 본다.
7. **형태를 기록한다.** 비트마다 지배 형태(곡선·원·방사·기하·유기·직선·흔적)와 하드/소프트 엣지, 반복되는 모티프.

## 3. 무엇을 보나 (핸드북 장별 렌즈)

핸드북 카드가 곧 질문지다. 해당하는 것만 쓰고, 없는 것은 억지로 찾지 않는다.

**타이밍 (05장)**
- 같은 동작 문법이 반복되나? 반복될 때 모으기(차지+플래시)는 길어지고 맞히기(차지 끝→타격)는 짧아지나? (TI03, TI05)
- 큰 피크 직전에 밝기 누르기가 있나? 몇 프레임? 클라이맥스로 갈수록 짧아지나? (TI04)
- 피크 간격이 끝에서 좁아지나? (TI05)
- 새 형태가 등장한 뒤 홀드가 있나? 등장은 몇 f, 홀드는 몇 f? (TI02)
- 임팩트 프레임(무채색·반전)이 있나? (TI06) 클라이맥스 뒤 밝기 천장과 장면 색은 어떻게 정리되나? (TI08)

**밸류 (02장)**
- 단계별 대표 L*와 면적. 코어 면적이 작은가? (VA04, VA05)
- 상태가 바뀔 때 밸류 뼈대가 유지되나? (VA06)
- 동시에 밝은 것이 둘일 때 한쪽이 양보하나? (VA07)

**컬러 (03장)**
- 밝기 단계마다 색상이 어디로 움직이나(램프)? 어두운 끝이 배경색으로 모이나? (CO06)
- 코어는 순백인가, 색을 품은 백색인가? 순백은 언제 쓰나? (CO09)
- 색 전환 경로가 회색을 지나나? 층마다 속도가 다른가? (CO08, TI07)
- HSV S와 선명도 순위가 뒤집히는 색 쌍이 있나? (CO05)

**빛 (04장)**
- 장면에 남는 빛(바닥·주변이 밝아짐, 화면 노출 상승)이 있나? (LI01)
- 화면 레벨 장치: 노출, 비네트, 아나모픽 스트릭, 색수차, 인서트. (LI05)

**형태·구성 (01·06장)**
- 비트별 형태 흐름. 결정적인 행동일수록 선이 곧아지나? (SH03)
- 질서 → 혼돈 순서가 있나? (SH04) 반복 모티프는? (SH08)
- 구도 축(이동 경로가 오가는 선)이 있나? (CP06) 1·2·3차 위계는? (CP01)

## 4. 해석 규칙

- **숫자는 측정한 것만.** 페이지와 노트에 쓰는 모든 수치는 measure.py 출력이나 data.json에서 나와야 한다. 근사한 그래프(단순화)는 그렇다고 표시한다.
- **해석은 해석이라고 쓴다.** "분석자 해석" 또는 "~로 읽힌다". 제작 의도를 단정하지 않는다.
- **용어는 핸드북 용어로.** 밝기 누르기(피크 직전 밝기를 빼는 프레임), 모으기 / 맞히기, 코어·바디·엣지·헤이즈, 장면에 남는 빛, 임팩트 프레임, 램프.
- **카메라가 바뀌는 인서트**(클로즈업 등)는 색상 분석에서 빼고 `impact_range`에 넣는다.
- **기준 프레임(plate)** 은 이펙트가 없는 프레임. 첫 프레임에 이미 이펙트가 있으면 이펙트가 가장 적은 프레임을 골라 extract.py를 `--plate N`으로 다시 돌린다.

## 5. 자주 나오는 함정

- 카메라가 움직이는 영상은 "이펙트 픽셀" 판정이 배경까지 잡는다. 그 경우 면적·밝기 단계 비율은 쓰지 않거나 "카메라 이동 구간 제외"를 명시한다.
- 블룸·톤매핑·압축 때문에 ±2 L* 오차는 기본이다. 2 이하 차이로 주장하지 않는다.
- 화면 녹화본(워터마크, 드롭 프레임)은 `dupes`로 중복을 먼저 확인한다.
- **fps가 다른 사례 비교.** 페이지와 Index의 프레임 수는 측정한 영상 fps 그대로 쓴다. 핸드북 카드(星光啊는 30fps)와 비교하는 반영안·카드 문장에는 초를 같이 쓴다: "모으기 39f(60fps, 0.65s)". 비율(×2.6 같은)은 fps와 무관하니 그대로 비교한다.
- 대상이 움직이거나 쓰러지면 기준 프레임이 맞지 않는 구간이 생긴다. `--plate`를 구간별로 주고, 어느 기준으로도 깨끗하지 않은 구간은 method와 Index에 적는다.
- 이펙트가 화면에서 작으면 강도 값이 전체적으로 낮다. peaks의 기본 하한은 영상 기준으로 자동 계산되지만, 그래도 놓치는 발사 섬광이 있으면 `--min`을 낮춰 다시 본다.

## 6. 평가 쓰는 법 (06 REVIEW)

평가는 분석 페이지에서 **가장 비중이 큰 섹션**이다. 질문은 하나다. "이 레퍼런스를 내 게임 이펙트에 그대로 따라 해도 되나?" 답은 세 덩어리로 낸다.

1. **총평**(`verdict`): 한 문장 + 평가 지도 + 그대로 가져온다 / 바꿔서 가져온다 / 그대로 쓰지 않는다
2. **잘된 점**(`review`, side good): good · counter 3–5개
3. **아쉬운 점**(`review`, side bad): weak · risk 3–5개

### 6.1 네 종류

| kind | 뜻 | 반드시 쓸 것 | 핸드북으로 가는 곳 |
| --- | --- | --- | --- |
| `good` | 원리대로 해서 잘 작동한다 | 수치 + 이 영상에서 작동한 조건 + 가져오기 | 해당 카드 실측 근거(보강) |
| `counter` | 원리와 다른데 잘 작동한다 | 어긴 원리 + 그래도 작동한 조건 + 예외가 끝나는 경계 | 해당 카드 충돌·주의(반례) |
| `weak` | 원리와 다르고 실제로 약해 보인다 | 측정 근거 + 화면 근거(프레임) + 목표 수치가 있는 개선안 + 확인 방법 | 해당 카드 충돌·주의(실패) |
| `risk` | 영상으로는 좋지만 게임에 가져오면 위험하다 | 게임 조건(조작, 반복, 카메라, UI, 광과민성) + 대응 | 해당 카드 충돌·주의(게임 적용 주의) |

레퍼런스는 대부분 잘 만든 작품이다. **핸드북과 다르다고 바로 weak로 쓰지 않는다.** 화면에서 실제로 약해 보이는 근거(측정값과 프레임 둘 다)가 있을 때만 weak다. 다르기만 하고 약해 보이지 않으면 counter다.

### 6.2 검사표: 후보를 찾는 순서

감으로 찾지 않는다. 아래 검사를 전부 돌리고, 걸린 것을 후보로 올린 다음 프레임을 Read로 직접 보고 판단한다. 걸리지 않은 검사도 "통과"로 근거가 된다(잘된 점 후보).

| 영역 | 검사 | 명령 | 후보 기준 |
| --- | --- | --- | --- |
| 길이 | 전체 길이, 첫 타격·최대 타격 시각 | meta.json, `peaks` | 최대 타격까지 게임 예산 초과 → risk. 예산을 모르면 일반 스킬 1s 안팎, 궁극기 3s 안팎으로 가정하고 "가정"이라고 쓴다 |
| 누르기 | 큰 피크 직전 밝기 누르기 | `peaks`, `col 1 a-b`, `col 10 a-b` | 가장 큰 피크 앞에 누르기 없음 → weak 후보. ROI 최대 L\*(2·3열)나 상위 0.2%(17열)만 내려가면 밝기가 아니라 면적이 준 것일 수 있다. 1열(이펙트 상위 5%)과 10열(면적)을 같이 보고 '밝기 누르기 n f + 면적 축소 m f'로 나눠 쓴다 |
| 섬광 | 1초 안 섬광 횟수 | `flash` | 3회 = 상한 → risk, 4회 이상 → weak급 risk. 근사 검사라고 쓴다 |
| 밝은 면적 | 코어 면적(data 7열 = **이펙트 픽셀 중** 코어 비율), 단계 비율 | `palette`, `col 7 a-b --over 10` | 코어가 이펙트의 10% 넘는 프레임이 2f 이상 → weak 후보. 1f뿐이면 counter 후보. 이펙트가 작으면 비율이 부풀려지니 화면 대비(7열 × 10열 ÷ 100)가 1% 아래면 후보에서 뺀다. 글에는 '이펙트의 n%'처럼 기준을 밝힌다 |
| 가림 | 대상 실루엣이 밝은 이펙트에 덮인 비율 | `cover a-b --crop <대상>` | 30% 넘는 구간이 2f 이상 → weak / risk 후보. 대상이 움직이거나 쓰러지면 plate 구간마다 crop을 따로 잡는다. 덮여도 실루엣이 어두운 음각으로 남으면(strip으로 확인) counter 후보 |
| 주목 | 두 주체 중 누가 밝은가 | `focus` 원값과 `--relative` 둘 다, `cover`(ROI별 L\*≥85 면적) | 차지·예비 구간의 절반 넘게 주인공 아닌 쪽이 밝음 → weak 후보. 기준 밝기가 높은 쪽은 relative에서 천장(100) 때문에 불리하다. ROI 최대 L\*는 작은 밝은 점 하나로도 높으니, 둘 다 밝다는 주장은 `cover`로 밝은 면적도 확인한다 |
| 색 경로 | 전환 중간의 선명도 | `cpath a-b [--crop <물체>]` | 색상이 30° 넘게 바뀌는 전환에만. 중간 프레임 선명도가 양 끝 중 낮은 쪽보다 10 넘게 낮음 → weak 후보. 화면 전체 값은 다른 요소(리본, 반짝임)가 섞여 중앙값이 내려갈 수 있으니 전환하는 물체 crop으로 다시 잰다. **HSV S만 떨어지는 건 착시라 쓰지 않는다**(VA02) |
| 밸류 고정 | 상태 전후 밸류 뼈대 | `lstats 전,후 --crop <같은 영역>`, `palette` 단계 면적 | 색상이 30° 넘게 바뀌는 상태 변화에만 VA06 평가를 쓴다. 단계 대표 L\*는 단계 구간 안의 중앙값이라 거의 늘 비슷하게 나온다. 근거는 같은 영역 L\* 분포(중앙값·90·99%)와 단계 면적 비율로 댄다 |
| 화면 덮음 | 이펙트 면적(data 10열) | `col 10 a-b --over 50` | 50% 넘는 구간이 0.5s 이상 → risk(시야 가림) |
| 카메라 | 인서트·컷 | 컨택트 시트 | 카메라 컷 → risk(고정 카메라 게임) |
| 여운 | 장면색 복귀 | `scene a-b` | 1.5s 넘게 안 돌아옴 → weak 후보 |

아쉬운 점이 하나도 안 나오면 검사를 다시 본다. 그래도 없으면 risk만이라도 쓴다. 영상과 게임은 조건이 늘 다르다.
측정이 다른 측정과 어긋나면(예: HSV S는 떨어지는데 선명도는 오른다) 눈에 가까운 쪽(명도, 선명도)을 믿고, 어긋남 자체를 근거로 적는다.
`hue`·`cpath`의 양 끝은 구간의 첫·마지막 프레임이다. 이펙트가 막 생기거나 사라지는 프레임이 끝에 오면 값이 흔들리니, 양 끝이 다 형성된 프레임이 되게 구간을 잡는다(strip으로 확인).
**평가에서 다시 잰 값이 앞 섹션(01–04) 카드와 어긋나면 그 카드도 고친다.** 페이지 안에서 평가와 분석이 서로 다른 말을 하면 안 된다.

### 6.3 항목 하나의 구조

| 필드 | 쓰는 것 | 규칙 |
| --- | --- | --- |
| `title` | 판단 한 줄 | 원리 문장 또는 결과 문장. "주목을 너무 늦게 넘긴다", "1초 안 섬광 3회, 기준 상한" |
| `what` 관찰 | 무엇을 했나 | **측정 수치만**. 1–2문장. 핵심 수치는 `<b>` |
| `why` 왜 | 왜 작동하나 / 왜 약한가 / 왜 위험한가 | 지각 원리 + 핸드북 원리를 풀어 쓴 문장(카드 ID 금지). good은 "이 영상에서 작동한 조건"(길이, 앞뒤 밝기, 배경 L\*, 크기)까지. 해석이면 "(분석자 해석)" |
| `ev` 근거 | 수치 칩 2–4개 | `[["라벨","값"]]`. 값은 measure.py 출력 그대로 |
| `take` 가져오기 | good · counter | 내 작업 규칙 한 줄. **숫자를 넣는다**(차이 3 이하, 1f, 7f 간격). fps가 다르면 초도 쓴다. counter는 예외가 끝나는 경계도("2f 넘으면 VA05로 돌아간다") |
| `fix` 개선안 | weak · risk | **목표 수치**가 있는 한 줄. "결정 명도 87 안팎으로 F160부터", "9f 안에 50% 아래로". 목표값은 측정이 아니라 제안이니 근거 수치와 섞지 않는다 |
| `check` 확인 | weak는 필수, 나머지는 권장 | 고친 결과를 무엇으로 확인하나. `measure.py focus 141-222 → 시전체가 밝은 구간 40f 이상` |
| `thumbs` 그림 | 1–4장 | 전/후, 문제 프레임/정상 프레임, 단계별. 라벨은 짧게("차지 초반", "−17%") |
| `spark` 그래프 | 권장 | 근거 수치가 시간에 따라 변하면 미니 그래프. 문제 구간은 `win`, 핵심 프레임은 `mark` |
| `card`, `frames` | 필수 | 카드 ID 1–2개, 프레임 구간 |

문장 수: 필드 하나에 1–2문장. 항목 하나는 카드 한 장 높이를 넘지 않는다.
글 속에 카드 ID를 쓰지 않는다. "VA07은 …라고 한다" 대신 원리를 풀어 쓴다("화면에 오래 남는 요소가 먼저 밝기를 낮춰야 시선이 넘어간다"). 프레임은 `F154`, `F40–46`으로 쓴다(페이지에서 눌러서 확인된다).

**예시 (weak)**: 星光啊 W1
- 관찰: 2차 차지 F141–222(82f) 중 시전체가 결정보다 밝은 것은 9f뿐. 결정 최대 명도 96 → 87로 천천히 내려간다.
- 왜 약한가: 화면에 오래 남는 요소(결정)가 먼저 밝기를 낮춰야 시선이 새 주인공으로 넘어간다. 넘기기가 마지막 10f에 몰려 77f 차지 대부분 시선이 결정에 머문다(분석자 해석).
- 근거: 시전체가 밝은 구간 9 / 82f · 결정 최대 명도 96 → 87 · 넘기는 시점 F210
- 개선안: 결정을 F160부터 명도 87 안팎으로 낮춰 둔다. F218 누르기와 F219 빔은 그대로.
- 확인: `focus 141-222` → 시전체가 밝은 구간 40f 이상

### 6.4 총평 쓰는 법

- `line`: 한두 문장. "무엇을 그대로, 무엇을 바꿔서, 무엇은 쓰지 않는다" 순서.
- `copy` 그대로 가져온다: good 중 게임 조건에서도 그대로 통하는 것.
- `adapt` 바꿔서 가져온다: counter(조건부), weak(고쳐서), 길이·카메라처럼 형식만 바꾸면 되는 risk.
- `avoid` 그대로 쓰지 않는다: 안전·가독성 risk(섬광, 화면 덮음 등).
- 각 줄 끝에 카드 ID와 항목 번호(G1, W2…). 항목 번호는 템플릿이 잘된 점 G1…, 아쉬운 점 W1… 순서로 자동으로 붙인다.
- 총평의 모든 줄은 아래 항목 하나 이상과 연결된다. 항목에 없는 말을 총평에 새로 쓰지 않는다.

### 6.5 쓰지 않는 것

- 점수표(○△✕, 10점 만점). 사례가 쌓이기 전에는 기준이 흔들린다.
- 취향어("예쁘다", "고급스럽다"), 근거 없는 제작 의도 추정.
- 핸드북 원리를 그대로 옮긴 문장만 있는 good. 이 영상에서 작동한 조건이 없으면 평가가 아니라 요약이다.
- 측정 수치 없이 형태 관찰만 있는 항목(모티프 반복 등). 그런 내용은 04 형태 섹션 카드에 둔다.

## 7. 유형별 렌즈: 투사체

영상에 날아가는 덩어리(투사체·혜성·탄환·화살)가 있으면 **05 PROJECTILE** 섹션을 넣고, 핸드북 `10 유형/투사체 — 유형 노트`의 사례 비교 표에 이 사례를 더하는 반영안을 만든다. 사용자가 중점으로 보는 것은 **형태감 · 질감 · 컬러 변화 · 쉐입**이고, 부가로 비행·발사·착탄·바닥 대비를 본다.

### 7.1 재는 순서

1. 비행 구간을 정한다: 발사 섬광이 끝난 직후 ~ 착탄 직전. 섬광 프레임이 들어가면 덩어리가 깨진다.
2. 머리 위치를 읽는다: `measure.py WORK grid f1,f2,... out.jpg`로 격자 그림을 만들어 Read로 보고, 4–6프레임의 머리 좌표(스프라이트 셀)를 적는다. 여러 발이 엇갈리면 한 발씩 따로 적는다.
3. 따라가며 잰다: `projectile.py WORK a-b --follow "f:x,y;f:x,y;..." --name 이름`
4. **`mask_이름_1.jpg`를 반드시 본다.** 노랑으로 칠한 영역이 몸통 전체를 덮어야 한다. 머리만 잡히면 `--lmin`을 낮추고(45–55), 안개·바닥 빛까지 잡히면 올리거나 `--radius`를 줄인다. 문턱값을 바꾸면 길이·윤곽 값이 달라지니, 최종 값의 문턱값을 notes에 적는다.
5. 발사·착탄은 data로 잰다: 발사 섬광 프레임과 착탄 프레임의 강도(12열)·이펙트 면적(10열), 착탄 직전 2–3f의 강도. 바닥 명도는 `measure.py bg`.

### 7.2 값의 뜻 (projectile.py 출력)

| 렌즈 | 값 | 뜻 |
| --- | --- | --- |
| 형태감 | 길이 · 두께(화면 폭 %), 길이÷두께, 길이 범위 | 덩어리의 비율. 비행 중 길이 변화는 속도감 |
| 질감 | 윤곽 선명도(머리 / 꼬리), 결 거칠기 | 윤곽 선명도는 경계의 밝기 기울기, 클수록 하드 엣지. 결 거칠기는 덩어리 안 잔무늬(줄무늬·노이즈) |
| 컬러 변화 | 머리→꼬리 8구간 명도·선명도·색상, 비행 시작→끝 머리 색 | 공간 램프와 시간 변화 |
| 비행 | 프레임·초, 화면 폭 대비 속도(배/초), 직진도, 방향 변화 | 직진도 1 = 직선. 머리 위치는 5f 이동평균이라 방향 변화는 대략값 |
| 쉐입 | (그림으로 본다) | `heads_이름.jpg`로 머리 모양·몸통 모양·입자를 직접 보고 쓴다 |

길이·속도를 화면 폭 대비로 쓰는 이유: fps와 해상도가 다른 사례끼리 비교하려고. 프레임 수 비교는 초로 바꾼다.

### 7.3 무엇을 보나 (유형 노트의 질문지)

- **형태감**: 머리가 1차로 먼저 보이나? 길이÷두께는(한 발 4 안팎 / 무리 2 안팎)? 비행 중 길이가 변하나?
- **질감**: 머리 윤곽이 꼬리보다 또렷한가(이론: 하드한 머리, 소프트한 꼬리)? 반대라면 머리 위치를 무엇이 대신 알려주나(가장 높은 명도, 작은 하드 포인트)? 몸통 결이 방향을 보여주나?
- **컬러 변화**: 머리 → 꼬리로 명도가 얼마나 내려가고 선명도는 어떻게 되나? 색상 이동 폭은? 비행하며 머리 색이 식나, 밝아지나?
- **쉐입**: 머리 실루엣이 스킬 모티프인가? 몸통은 몇 줄인가, 입자는 어디에 몇 개인가? 궤적은 직선인가 크게 도나?
- **부가**: 착탄이 발사보다 큰가(면적·강도 배수)? 착탄 직전 밝기가 빠지나? 바닥과 명도 차가 30 이상인가, 색 계열이 같으면 무엇으로 분리되나?

### 7.4 05 PROJECTILE 카드 쓰는 법

- `type: "projectile"` 카드 하나에 투사체 1–3개(`items`). 필드는 config_schema.md.
- `profile`·`time`·`path`는 `tracks_이름.json`에서 그대로 옮긴다(profile_mid → profile, head_start/end → time, path → path).
- 렌즈 글은 수치 칩 2–3개 + 한두 문장. 이론과 다르면 그렇다고 쓰고 이유를 적는다(평가의 counter 후보).
- 평가(06 REVIEW)와 같은 사실을 말할 때는 숫자를 맞춘다.
